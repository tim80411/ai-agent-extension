# 規劃型工單：從需求到 Jira（jira-ticket-authoring）

這支 skill 把要做的事寫成「讀的人照著就能做、不必回頭問」的故事與工單，再建進 Jira。

寫錯的成本落在讀的人身上。草稿裡每個「待確認」、每個查得到卻沒查的事實，都要有人在十幾張單之間來回拼湊。所以先查清楚，再把只有人知道的決定一次問完，最後才動筆。

流程分六段，前面加一個讀快照的準備步驟。每段有完成條件，條件沒到就不進下一段：

```
（讀專案快照）→ 查 → 集中提問 → 出草稿並確認（3 張以上）→ 列待裁示 → 建單 → 回查回報
```

## 什麼時候用（與不該用）

| 情境 | 用這支？ | 改用 |
|---|---|---|
| 把下一期目標、會議結論或需求拆成 Jira 故事與工單；寫工單草稿；開一批單 | 是 | — |
| 只開一張規劃型任務 | 是（跳過第三段） | — |
| 補充或修正既有工單的描述、範圍、驗收 | 是 | — |
| Bug、客訴、維運異常回報；只問估點或優先級怎麼定 | 否 | 環境裡有對應的開單 skill 就用它 |
| 查詢、轉狀態、記工時、改指派等操作既有工單 | 否 | `jira-cli` |
| 寫給 coding agent 照著實作的檔案式 Story（SPEC.md） | 否 | `spec-writing` |
| issue 存在 repo 檔案裡（markdown＋frontmatter） | 否 | `file-based-issues` |

## 準備：讀專案快照

**Goal**：同一個專案的站台參數、Epic、標題寫法、標籤規則與踩過的坑，不必每次重新摸索。

**Actions**：

1. 確認是哪個 Jira 專案。使用者沒指明時：在 repo 裡工作的話，先跑
   `node ${CLAUDE_PLUGIN_ROOT}/scripts/pm-config.mjs show --json`，結果是 `provider: jira` 的 profile 時，
   `settings.project_key` 是預設候選，仍要跟使用者確認；沒有結果（exit 4）就直接問。
2. 找專案快照 `~/.config/pm-toolkit/jira/{專案代號小寫}.md`（設了 `$XDG_CONFIG_HOME` 時，在
   `$XDG_CONFIG_HOME/pm-toolkit/jira/`）。有就整份讀完，再進第一段。
3. 沒有快照，直接從第一段開始查，並記下：第二段的問題清單最後要加一題「要不要把這次查到的存成專案快照？」。

快照只放本機、不進任何 repo：裡面有站台網址、角色對應、內部連結。放在 `~/.config/pm-toolkit/`
而不是 `~/.claude/`，理由跟 pm-toolkit 的設定檔一樣：使用者自己的設定，不該跟工具的安裝狀態綁在一起。

快照只是加速，不取代查證。每次仍照第一段查，以查到的為準；查到的跟快照不同時，以查到的為準，並提醒使用者更新快照。

完成條件：專案代號已確認；有快照的已讀完，沒有的已記下要在第二段問。

## 一、查

**Goal**：查得到的事實由你查清楚，查不到的整理成問題，不讓讀工單的人替你查。

**Actions**：

先確認三件事：哪個專案、新建還是修正既有單、大約幾張。

再查下面這些。查法與實例在 [01-preflight.md](references/01-preflight.md)。

- **Jira**：重複工單、Epic 與歸屬判準、同 Epic 的標題寫法與最大序號、人員帳號、當期 Sprint 與剩餘工作天、類型名稱、Sprint 欄位、使用者指定的範例單。
- **要寫成「前置」的既有工單**：讀它的父單與狀態，確認它真的是這件事的前置。
- **已記錄的前提**：記憶、專案的決策紀錄、名詞表、專案快照的「已記錄的前提」。寫出來的內容要跟它們一致。
- **現行畫面**：「照現有畫面重做」的工單，先開現行網站走過一遍。
- **既有元件或格式**：新資料要接上它時，誰驗證接得起來。
- **人員與角色**：記憶或快照裡的寫法，先向使用者確認再用。
- **範圍依據**：取最新的正式紀錄（會議頁比聊天訊息新）。

完成條件：每一項都有結果——查到的事實，或「查不到，要問」。每個「要問」都已寫進下一段的問題清單。

## 二、集中提問

**Goal**：只有使用者或 PM 知道的決定，一輪問完，問完才寫。

把它們寫成「待確認」撒進各張單，等於把成本轉給讀的人。（實例：一批 14 張的第一版留了 73 個待確認，使用者花一天逐題回了 31 題。）

**Actions**（問題類型與範例見 [01-preflight.md](references/01-preflight.md)）：

- 一題一個決定。會影響多張單的前提題排最前面。
- 每個選項附真實資料列，或工單裡實際會寫出的句子。自創的抽象標籤會讓使用者先反問「這是什麼意思」。
- 每題附建議答案。預設通常是「沿用現行」或「縮範圍」，不是補新功能。
- 4 題以內用 AskUserQuestion 工具問。更多時列成編號清單，讓使用者用「1a、2b、其餘採建議」一次回覆。
- 準備步驟記下要問快照的，把「要不要存成專案快照」放在清單最後。

工單裡只留真的還沒人能答的待確認，並寫明由誰答。

**回答若是前提，回掃全部。** 任何時候收到回答（這一段、草稿階段都算），先判斷它會不會影響多張單。會的話，把所有故事與工單掃一遍，不只改那一題指到的那一張。

完成條件：清單每一題都有答案，或使用者明說「這題先留待確認」；前提類的答案已回掃過全部故事與工單。

## 三、出草稿並確認

一次 3 張以上，或使用者要先看草稿時才有這一段。只開 1～2 張時跳過，把完整預覽（欄位＋描述）放進第四段的待裁示。

**Goal**：使用者先快速看過故事，再挑工單細看，確認後才進入建單。

**Actions**（照 [03-draft-delivery.md](references/03-draft-delivery.md) 交付）：

- 使用者故事與工單分開放。使用者的原話：「我喜歡你給我使用者故事跟工單分開，我可以先快速檢視使用者故事而不用細看工單」。
- 故事與工單照 [02-description-format.md](references/02-description-format.md) 寫。
- 「還沒定的事」與「這一版改了什麼」放在草稿文件裡，不進工單。
- 使用者會直接在線上改，包括重排編號。每次動手前先讀使用者改了什麼；認工單用標題。

完成條件：使用者確認草稿可以進入建單。

## 四、列待裁示（固定步驟）

**Goal**：Jira 上的每個動作（掛哪個 Epic、指給誰、進不進 Sprint）都經過使用者同意。

建單前一律先列出計畫與疑義，等使用者同意才動手；資訊齊全時也一樣。內容的決定已在第二段問完，這一段只處理 Jira 上的動作，問過的不再問。

**Actions**——逐項列出：

- **容量**：新單進 Sprint 會不會超出剩餘天數，誰的負載最重。
- **相依**：前置工單還在 backlog 時，本單在 Sprint 內能交付到什麼程度。
- **Epic 歸屬**：每張單掛哪個 Epic；跟 Epic 判準衝突時明講。
- **指派**：要不要指派、指給誰（Story 的規則見第五段）。使用者只說角色時，確認是誰。
- **交付物**：看不出交付形式（文件、簡報、設計檔）時問。
- **與既有規範或文件的衝突**：逐項列出雙方內容，給選項與建議。
- **既有工單的處理**：擴充、另建或補註。
- **標籤**：照專案快照的標籤規則。快照沒寫時，看近期同類工單實際帶什麼，提建議；拿不準就列在這裡問。要加的主題標籤也列在這裡。
- **工單連結**：要不要建、建哪一種（見第五段）。

每項給選項並標出建議，讓使用者能回「1a、2b、其餘採建議」。最後附一張「預計執行內容」表，工單用標題認：

| 工單（標題） | 動作 | 類型 | Epic | 指派 | 去向 |
|---|---|---|---|---|---|
| 快速型錄品項選擇：自動挑選、換品項與篩選 | 新建 | 故事 | E10（ABC-70） | 不掛 | Backlog |

完成條件：使用者明確同意（例如「開吧」「照建議」）。

## 五、建單

**Goal**：照裁示建好或改好每一張單；失敗時不建出重複的單。

### 欄位

| 欄位 | 規則 |
|---|---|
| 類型 | 使用者看得到、能驗收的功能用故事；環境架設、規則或文件編撰、資料彙整這類不直接面向使用者的工作用任務。專案既有工單的分法不同時，以專案為準。類型名稱可能是在地化名稱（中文介面的站台是「故事、任務、大型工作、子任務」），用 `getJiraProjectIssueTypesMetadata` 查該專案實際的名稱，查到的值記在專案快照。 |
| 標題 | 沿用專案既有寫法，以第一段查到的為準，不套別的專案的寫法。 |
| Parent | 第四段裁示的 Epic。 |
| 指派 | Story 不掛人，負責人掛在 Story 底下的子任務：Story 是需求層級的歸屬，實際執行者掛在子任務。Task 依裁示。沒裁示的不指派。 |
| 優先度 | 預設 Medium；使用者指定才改。 |
| Story Points | 只填使用者或 PM 給的點數（費式 1、2、3、5、8、13；8 以上在待裁示建議拆）。沒估就留空，草稿寫「待估」。範圍變動過的舊估值，草稿寫「N（待重估）」，建單時照裁示填舊值或留空。 |
| 標籤 | 照第四段裁示的帶。標籤規則先看專案快照（例如團隊要求每張單帶某種日期標籤，連子任務也帶）；快照沒寫就看近期同類工單實際帶什麼；拿不準的已在第四段問過。主題標籤不新造：先查既有的、提建議、確認後才加。 |
| Sprint | 進當期 Sprint 才填；進 backlog 不填。Sprint 欄位的 ID 因站台而異（通常是某個 `customfield_NNNNN`，值是 Sprint ID 數字），先查，查到的值記在專案快照。 |

**子任務**：子任務由執行者自己開、自己估。本 skill 只在使用者裁示要指派時，在 Story 底下建一張子任務、把人掛在子任務上。標題前綴沿用專案寫法（看同一父單底下既有的子任務）。

**工單連結**：相依項目的「前置」對 `blocks`（前置單 blocks 本單），「關聯」對 `relates to`。只建第四段裁示過的。

### 描述

照 [02-description-format.md](references/02-description-format.md) 的 9 節，以 markdown 送出。

同批多張單先建被依賴的，後面的單才能引用它的工單號。草稿裡用「T-NN（標題）」指的同批工單，建完回填成工單號。

### 建單工具

用 `createJiraIssue`，參數以工具實際 schema 為準：

- `cloudId`：專案快照裡的值；沒有快照就用 `getAccessibleAtlassianResources` 查。
- `projectKey`、`issueTypeName`、`summary`。
- `description`：直接傳 markdown 字串，不帶 `contentFormat`。要傳 ADF 時才同時帶 `contentFormat: "adf"`，否則 ADF 會被當成純文字存進去。
- `assignee_account_id`：`lookupJiraAccountId` 查到的 ID；不指派就不帶。
- `parent`：建子任務時帶父單 key。
- `priority`、`labels`、Story Points、Sprint 放在 `additional_fields` 裡，例如 `{"priority": {"name": "Medium"}, "labels": ["{標籤}"]}`。寫在最外層會被 schema 擋下。
- 掛 Epic：依工具 schema 帶（`parent` 或 `additional_fields`），建完回查 parent 是否正確。
- 不帶 `transition`：新單留在專案預設的起始狀態。

建單失敗時，先查是不是其實已經建出來，再決定要不要重送；換參數盲目重試會建出重複的單。查法：`project = {KEY} AND summary ~ "{標題}" AND created >= -10m`（時間窗要寫，否則會撈到同名舊單）。

- 已建出來：回報工單號，用 `editJiraIssue` 補齊缺的欄位。
- 沒建出來：把錯誤訊息原文給使用者，再決定怎麼做。
- 建單畫面沒有 assignee 或 labels 欄位而被擋：先用最小欄位（`projectKey`、`issueTypeName`、`summary`、`description`）建，再用 `editJiraIssue` 補標籤與指派。

### 修正既有工單

- 預設在描述最前面加一節「YYYY/MM/DD 更新註記」或「補充」，寫明現在的範圍跟原文哪裡不同；**原文保留**。註記只寫現在要做什麼，不寫誰在哪天指示（理由見 02-description-format.md 的「不寫歷史敘述」）。
- 編輯描述要送出完整內容。先讀出完整原文，逐字保留（含原有錯字），只加新的一節。
- 刪除或改寫原文，要使用者明確指示。刪了之後，在更新註記留一句說明刪了什麼。
- 改指派、改 Epic、改標題、加標籤，只做裁示過的，回報時逐項列出。
- 原本描述是空的，直接補上完整 9 節。

完成條件：每張單都建好或改好；失敗的已查明有沒有建出來。

## 六、回查回報

**Goal**：Jira 上的實際結果跟裁示一致，而且使用者知道哪些是你自己判斷的。

**Actions**：

1. **回查**：用 JQL 確認每張單的工單號、Parent、Sprint、指派、標籤都對。
2. **回報**分三組：進 Sprint 的、進 backlog 的、修正既有單的。每張附連結 `https://{站台}/browse/{KEY}`。
3. **列出自行決定的部分**：沒經過裁示、由你判斷的（優先度對應、標籤、範圍推定、讓位順序），逐項點出來請使用者過目。
4. **指派給他人的工單**：提醒使用者先過目內容，再通知對方。
5. **同步 Sprint 規劃文件**：Sprint 範圍有變動時，更新對應的規劃文件（工項表、時程節點、不納入範圍的說明、容量風險與讓位順序、資料來源註記）。先確認使用者要同步再動。
6. Sprint Goal 的文字工具改不了時，告訴使用者要在 Jira 手動調整。
7. **專案快照**：使用者在第二段同意存快照的，照 [04-project-snapshot-template.md](references/04-project-snapshot-template.md) 寫進 `~/.config/pm-toolkit/jira/{專案代號小寫}.md`；已有快照、但這次查到的事實跟它不同，提醒使用者更新，同意後再改。

完成條件：回查結果與裁示一致；不一致的已修正，或已告知使用者。
