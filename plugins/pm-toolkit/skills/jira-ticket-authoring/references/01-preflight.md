# 動筆前：查什麼、問什麼

SKILL.md 第一段（查）與第二段（集中提問）的細節。查得到的事實由你負責查；查不到、只有人知道的決定，進問題清單。

專案快照（`~/.config/pm-toolkit/jira/{專案代號小寫}.md`）只是加速。每次都查，以查到的為準。

下面的實例都來自同一次真實開單，產品與領域名詞已換成中性的。

## 一、Jira 上要查的

| 查什麼 | 怎麼查 | 為什麼 |
|---|---|---|
| 重複的單 | JQL 查當期 Sprint 與 backlog 的同主題工單；`fields` 只帶 `summary`、`status`、`assignee`、`parent` | 已有同主題 → 修正既有單，不重建；部分重疊 → 列進待裁示。fields 不限縮，結果會大到被存成檔案 |
| Epic | JQL `project = {KEY} AND issuetype = Epic`，再讀各 Epic 描述裡的歸屬判準 | 每張單掛哪個 Epic 要有依據。類型是在地化名稱的站台，JQL 不一定認得在地化名稱（實測過：寫中文「大型工作」查不到，加引號也一樣，要寫 `Epic`）。哪個寫法查得到，記在專案快照 |
| 類型名稱 | `getJiraProjectIssueTypesMetadata` | 建單的 `issueTypeName` 要用專案實際的名稱，可能是在地化名稱。查到的值記在專案快照 |
| 標題寫法與序號 | JQL `parent = {Epic key}` 列出該 Epic 底下的工單，看標題寫法與目前最大序號 | 標題沿用專案寫法；序號用猜的會撞號。實例：草稿寫 10.6 的那張，建單時已經是 10.7 |
| 人員 | `lookupJiraAccountId` 用顯示名稱查帳號 ID | 憑記憶填 ID 會指錯人 |
| 當期 Sprint | 從當期 Sprint 內任一工單讀出 Sprint ID 與結束日，算剩餘工作天 | 待裁示的「容量」要用 |
| Sprint 欄位 | 讀一張已在 Sprint 內的工單，或用 `getJiraIssueTypeMetaWithFields`，找出 Sprint 對應的 `customfield_NNNNN` | 欄位 ID 因站台而異。查到的值記在專案快照 |
| 標籤慣例 | 專案快照的標籤規則；沒有就 JQL 查近期同類工單（同 Epic、同類型），看實際帶什麼 | 團隊可能有固定標籤規則；規則跟實際做法對不上時，列進待裁示 |
| 範例單 | 使用者指定的範例單先讀 | 格式以它為準 |

## 二、會讓工單寫錯的事實

下面幾項都是上一批工單實際寫錯的地方，而且都查得到。

### 1. 要寫成「前置」的既有工單：查父單與狀態

引用既有工單當前置之前，讀它的 parent 與 status，確認它真的是這件事的前置，而且還沒完成。

實例：第一版把三張既有工單寫成型錄系統後端的環境前置。它們其實是另一個示範專案（線上呈現範例）底下的子任務，而且早已完成。最終版改成：

> 依賴：無。關聯：示範用的線上呈現範例專案（{三張子任務的工單號}，{父單號} 的子任務，已完成），做法可參考，但不是型錄系統的環境。

### 2. 已記錄的前提：寫之前對一次

讀記憶、專案的決策紀錄與名詞表、專案快照的「已記錄的前提」，列出跟這批工單有關的前提。寫出來的範圍、驗收、相依都要跟前提一致。前提看起來過時了，就進問題清單問，由使用者決定。

實例：記憶早就記著「商品資料系統除了收商品資料，不當其他產品的後端或資料庫」，第一版卻寫「型錄系統後端連得到商品資料系統的資料庫」。使用者自己改成「不可以直連商品資料系統的資料庫，用商品資料系統匯出的資料源」。

### 3. 照現有畫面重做的工單：先看畫面

用瀏覽器開現行網站，把工單要重做的每一頁走一遍，再寫範圍。順手截圖，草稿會用到（截圖規則見 03-draft-delivery.md）。沒有瀏覽器工具時告訴使用者，並把「現行畫面還沒看過」寫進該工單的風險。

實例：截圖後才發現，「設定型錄條件」是首頁的彈窗，不是獨立一頁；其中一個品牌沒有「系列」這一層選項；商品類型選擇頁與品項選擇頁有工單沒提到的功能。

### 4. 既有元件或格式：「已經存在」不等於「不用處理」

元件、格式定義已經做好，不代表新資料接得上。每遇到一個就問：新資料接上舊東西，誰驗證接得起來？那個驗證就是一件工作，要寫進某張單的範圍。

實例：第一版把一個已完成的多規格商品元件列為排除，把組合商品在商品資料格式定義（JSON Schema）裡的定義當成現成參照。最終版各多出一件工作：確認元件顯示得出匯入新版商品庫後的多規格商品；後端 repo 與商品元件套件兩邊的組合商品 Schema 定義一致。

### 5. 記憶裡的人員與角色：先確認再用

記憶裡的人員、角色、誰負責什麼，可能已經變了。用之前列給使用者確認。

實例：第一版照舊記憶，把內容端的追蹤者寫成「商品編輯」；實際上是另一位 PM（內容端 PM）。

### 6. 範圍依據：取最新的正式紀錄

同一件事有多個來源時（會議頁、聊天訊息、舊文件），以最新的正式紀錄為準。例如每期的精煉會議頁比聊天訊息新。兩邊不一致的地方，進問題清單。專案以哪一種紀錄為範圍依據，記在專案快照。

## 三、集中提問

### 什麼該問

查不到、只有使用者或 PM 知道的決定。判斷方法：換一個人來寫，會不會寫出不同的答案？會，就問。

### 常見問題類型

上一批工單實際問過的問題類型。每次先檢查這幾類有沒有還沒定的：

| 問題類型 | 實例（當時的答案） |
|---|---|
| 每條線本期做到哪一步為止 | 型錄系統停在品項選擇頁；下單系統做到下單，對帳不開單 |
| 完成的量 | 匯入是「每種商品類型各有固定筆數的示範資料」，不是全量；錯誤回報留到大量匯入 |
| 誰執行、誰追蹤、誰開單；角色怎麼稱呼 | 類型對照表由各品類編輯填寫，我方 PM 彙整與開單 |
| 外部角色的工作，本期我方只收到什麼程度 | 類型對照表本期以繳交為主，只做彙整 |
| 來源列了、但本期可能做不完的步驟 | 「彙整後跟工程師對接」要寫進範圍，還是排到下一階段？ |
| 目標句是大目標，還是可交付的故事 | 「匯入率達到目標比例」是類型對照表的更大目標，不另開故事 |

### 怎麼問

**一題一個決定。** 會影響多張單的前提題排最前面。

**選項附真實的句子或資料列。** 讓使用者看到選了之後，工單會寫成什麼。

不要這樣（抽象標籤）：

> 匯入範圍：A. 示範　B. 全量

要這樣（工單裡實際會寫的驗收）：

> 匯入範圍：
> A.（建議）「組合商品、多規格商品的示範資料從舊格式轉成新格式，每種商品類型至少 {N} 筆。」
> B.「清單內的組合商品、多規格商品全部轉成新格式；不符合上架規範的不匯入，同步紀錄表看得到原因。」

為什麼：自創的抽象詞（例如「對照不到」）曾被使用者連續退回兩次、要求重講；改成附真實輸出後，一次就選了。

**附建議答案。** 未定的事，預設答案通常是「沿用現行」或「縮範圍」，不是補新功能。實例：範圍選擇要不要改用關鍵字 → 建議沿用現行的品牌與系列；品項篩選 → 沿用現行的分類。

**工具。** 4 題以內用 AskUserQuestion，選項的 `preview` 放實際會寫出的句子。題數更多時，在對話裡列成編號清單（每題附選項與建議），讓使用者用「1a、2b、其餘採建議」一次回。有草稿文件時，同一份清單也放進「還沒定的事」。

### 工單裡留下的待確認

問完還是沒人能答的，才留在工單裡。寫成括號註記，說明缺什麼；影響驗收的，在風險表寫誰確認、確認前哪幾條 AC 驗不了。

> 示範資料由後端工程師從舊版商品庫挑，數量不夠時請商品編輯提供（挑選方式待確認）。

> （風險表 Mitigation）開工前請商品資料系統後端確認分類的資料來源；確認前，AC-02、AC-06 無法驗收。

### 回答若是前提，回掃全部

收到一個回答，先判斷它只管這一張，還是會影響多張單的前提。是前提，就把所有故事與工單掃一遍。

實例：使用者回答匯出那一題時說「先由型錄系統去理解商品資料系統的資料模型（ERD）後提出匯出目標」。當時只改了匯出那張單。但這句話背後的前提是「型錄系統用商品資料系統匯出的資料，不直連商品資料系統的資料庫」，它同時推翻了環境那張單寫的「型錄系統後端連得到商品資料系統的資料庫」。沒有回掃，最後是使用者自己去改環境單。

判斷方法：把回答換成一句不帶工單編號的話。如果那句話在別張單也成立，它就是前提。

### 要不要存成專案快照

專案還沒有快照時，問題清單最後加一題：「要不要把這次查到的站台參數、Epic、標題寫法、標籤慣例存成專案快照？下次開單就不用重查。」同意的話，在 SKILL.md 第六段照 04-project-snapshot-template.md 寫。

## 完成條件

- 第一、二節每一項都有結果：查到的事實，或已進問題清單。
- 問題清單每一題都有答案，或使用者明說「先留待確認」。
- 前提類的答案已回掃過全部故事與工單。
