# 故事與工單的描述格式

寫任何一則故事或一張工單之前讀這份。依序是：故事格式、工單格式、寫作規則、完整範例。

範例與實例來自一次真實開單，產品與領域名詞已換成中性的；結構與細緻度照原樣。

## 一、使用者故事

故事給使用者快速檢視，寫短。依系統分組，組內依流程順序編號。

```
### {系統，例：商品資料系統／型錄系統／下單系統}

#### US-NN {標題}

- 故事：身為{角色}，我想要{要做的事}，這樣{得到的好處}。
- 驗收標準：
    - {一句話，可以檢查}
- 不在本期：{項目}（{誰承接，或何時再做}）。
- 依賴：{US-NN 或工單號}；…
```

- 驗收在故事裡寫成一句話。展開成 Given／When／Then 是工單的事。
- 基礎建設類（環境、網域、API 文件）標題加「（Enabler）」，故事寫「身為{工程師角色}，我需要…」。
- 一件事拆成多則故事時，加一行說明怎麼拆。例：「組合商品分三張做：US-04 規則、US-17 商品資料技術合約、US-05 匯入。」

## 二、工單

### 草稿裡的標頭

草稿分頁開頭先列欄位。建單時這些變成 Jira 欄位，不放進描述。

```
# T-NN｜[模組] 主題

- 對應故事：US-NN
- 專案：{KEY}
- 類型：Story／Task
- Epic（Parent）：{Epic 名稱}（{Epic key}）
- 建議規劃編號：{N.N}（開單前重查）
- Priority：{Medium，或裁示的值}
- Story Points：{點數／待估／N（待重估）}
- 指派：{不掛（Story 不掛人，負責人掛在子任務）／裁示的人}
- Labels：{照專案的標籤規則；還沒定就寫「待裁示」}
```

T-NN 只是草稿編號。Jira 標題照專案寫法（見專案快照的「標題寫法」；沒有快照就照第一段查到的）。

### 描述：9 節

```
# 1. Story Goal 目標
（任務類寫 Task Goal。一段話：要做什麼、為什麼、本期做到哪。）

# 2. User Story 使用者故事
* 作為 — {角色}
* 希望 — {要做的事}
* 以便 — {好處}

# 3. Scope 範圍
## 3.1 In Scope
* {項目}
（有畫面的工單，截圖放在這裡，見 03-draft-delivery.md）
## 3.2 Out of Scope
* {項目}：{誰承接，或何時再做}

# 4. Deliverables 交付內容
1. {交付物}

# 5. Acceptance Criteria 驗收條件
* AC-01 Given {前提}，When {動作}，Then {看得到的結果}。

# 6. Definition of Done 完成定義
* AC-01～AC-NN 全部通過
* …

# 7. Dependencies 相依項目
* **父**：{Epic}
* **前置**：{工單號，或 T-NN（標題）；沒有寫「無」}
* **後置**：…
* **關聯**：…

# 8. Risks 風險
| Risk | Impact | Mitigation |
| --- | --- | --- |
（真的沒有就寫「無。」）

# 9. References 參考
* [{標題}]({網址})，{需要時補一句：哪一節、哪個議題}
```

送進 Jira 時用上面的 `#` 標題。在草稿分頁裡，分頁標題已經是最大標題，各節改用粗體段落（**1. Story Goal 目標**），層級才不會打架。

### 各節寫法

- **Goal**：一段話。結尾不加「PM 裁示 YYYY-MM-DD」這類註記，理由見寫作規則 1。
- **Out of Scope**：每一項都指出誰承接（另一張單、下一階段、哪個角色），兩張單的範圍才不會重疊或漏掉。
- **Deliverables**：寫成品（API、頁面、文件、彙整好的表），不寫步驟。
- **Acceptance Criteria**：編號 `AC-NN`，一條一個看得到的結果。寫明誰在哪裡驗（「PM 在型錄系統前端網站…」）。用一般列點，不加勾選框（使用者刪過）。
- **Definition of Done**：
  - 工程類預設四條：AC 全部通過；程式碼通過 Code Review（至少 1 位 Reviewer）；相關文件已更新（寫出是哪份文件）；已部署到開發環境，或具備部署條件。
  - 非工程類：AC 全部通過；文件放在團隊找得到的位置；指定的確認人確認過（寫角色）。
  - 「SIT／UAT 測試通過」使用者自己刪掉過，不放。
- **Dependencies**：同批還沒開的單寫「T-NN（標題）」，建完回填工單號。
- **Risks**：寫這張單真的會遇到的阻礙（前置未完成、外部規格未定、資料缺欄位），Impact 寫 High／Medium／Low。
- **References**：見寫作規則 2。

### 選用的兩節

「Technical Scope 技術內容」（放在 Deliverables 之後）與「Suggested Tasks 建議工項」（放在 References 之前）預設不寫。只有專案既有工單本來就有這兩節，而且使用者要求時才加；加了之後節號順延。

為什麼預設不寫：工單只講「做什麼、做到什麼算完成」，不替執行者決定怎麼做。子任務由執行者自己開、自己估。

## 三、寫作規則

### 1. 不寫歷史敘述

工單是給執行者照著做的。過程寫進去，讀的人就分不清哪句還算數。決策過程留在草稿文件的「改動紀錄」或「還沒定的事」。使用者原話：「工單內不要有太多的歷史描述」。

不要：「〇月〇日 PM 指示本期只做彙整。原本還包含對接，範圍調整後改為只收表。依據：精煉會議。」

要：「本期以彙整為主；彙整後跟工程師對接，留到下一階段大量匯入時再推動。」

同類要拿掉的句型：「某月某日誰指示／回覆」「原本…後來改成…」「範圍調整後」「PM 確認本期做」「依據：…會議」。

### 2. 參考都是可點的連結

讀的人要能一鍵點過去核對。使用者原話：「參考一定要是具體的連結」。連結可以是 Jira、Confluence、SharePoint、程式庫網址、線上文件。

不要：「依據：精煉會議結論」

要：「[本期精煉會議頁](https://example.atlassian.net/wiki/spaces/TEAM/pages/100001)，議題六」

沒有連結可附的（同批還沒開的單、口頭回覆）不列在參考，關係寫在相依項目。各類連結的網址樣式記在專案快照。

### 3. 角色用工作上的稱呼

人會換，角色不會；「某某 lead」這種職稱在團隊裡也不一定存在。使用者原話：「反正沒有後端Lead，要馬是個產品後端或是PM」。做事或查事實的，寫各產品的角色（例：商品資料系統後端、型錄系統工程師、前端工程師）；範圍與分工的決定，寫 PM。專案用的角色稱呼記在專案快照。

不要：「由後端 lead 確認」「請〇〇實作」

要：「開工前請商品資料系統後端確認分類的資料來源。」

### 4. 不自己填數字、不自己做決定

數字一寫上去就像定案，讀的人不會再問。

不要：「Story Points：3」（沒有人估過）

要：「Story Points：待估」；範圍改過的寫「Story Points：5（待重估）」。

筆數、日期、人選也一樣：沒定的進問題清單，問不到答案的寫「（待確認：…）」。

### 5. 不自己縮範圍，也不自己加範圍

默默寫成「不在本期」，等於替 PM 做了範圍決定，而且沒人會發現。

不要：流程文件列了步驟 1 首頁、步驟 2 設定型錄條件，草稿直接寫「步驟 1、2：不在本期，尚無工單」。（實際發生過：使用者的回答是「一樣要重現」，後來補開了一張單。）

要：在提問那一輪問「本期從哪一步做到哪一步？」。定案後才寫進 Out of Scope，並指出承接，例：「型錄預覽之後的流程：本期停在品項選擇頁，由後續階段承接」。

反過來也一樣：來源沒列的工作不自己補成故事。目標句先分清是大目標還是可交付的故事。實例：「匯入率達到目標比例」是類型對照表的更大目標，為它多開的「分批跑匯入與統計」故事被使用者刪掉。

### 6. 非我方執行的工作：從我方的角度寫

驗收要由我方驗得了。別人的工作，我方只看得到交付的結果。

不要：作為 — 各品類編輯；驗收「編輯完成類型對照表的校正與複核」。

要：作為 — 我方 PM；希望 — 收到各品類編輯填好的類型對照表。驗收「四個工作表都填寫完成，每一列都註明對應的商品類型」。

### 7. 故事之間顆粒度對齊，依系統分組

一張單包四步、別張只有一步，點數與進度就沒辦法比。

不要：一張「組合商品」包了定規則、確認共識、定資料格式、匯入四步，其他匯入單只有「匯入」一步。

要：拆成「組合商品匯入格式規則編撰與確認共識」「組合商品資料技術合約（JSON Schema）」「組合商品匯入」三張；規則與匯入放商品資料系統組，技術合約放下單系統組。

### 8. 「怎麼做」只在它是限制時才寫

做法屬於執行者。只有「沿用現行」「不可直連某資料庫」這類會限制做法的事，才寫進範圍。

要：「自動挑選與換品項沿用現行做法，在前端計算。」

不寫：API 路徑怎麼設計、程式怎麼拆、要開哪些子任務。

### 9. 名詞用專案名詞表的寫法

程式裡的型別名、欄位名不是領域名詞。寫之前對一次專案的名詞表與已記錄的前提（見專案快照的「已記錄的前提」）。

實例：商品類型用商品編輯定的名稱。工單寫「組合商品」，不寫照程式型別名直譯出來的「多規格捆綁商品」。

## 四、完整範例

使用者確認過的成品，可以照著仿寫。產品與領域名詞換成中性的，工單號換成 `ABC-NN`，網址換成 `example.*`；結構、句子與細緻度照原樣。

### 故事範例

```
#### US-12 快速型錄品項選擇

- 故事：身為店家，我想要系統依我設定的數量自動挑好品項，並能逐項換品項、用分類篩選，這樣不用一項一項挑也能做出我要的型錄。
- 驗收標準：
    - PM 進入品項選擇頁時，系統已依商品類型設定自動挑好品項，品項都在 US-10 選的範圍內。
    - 頁面上方的已選商品類型統計，跟商品類型選擇頁設定的數量一致。
    - 已選品項列表顯示每一項在新版商品庫的商品資料。
    - 對任一項按「換品項」，換成範圍內同商品類型、還沒被選的另一項。
    - 篩選條件沿用現行的分類，篩選後只顯示該分類的品項。
    - 本期停在品項選擇頁，頁尾「下一步」不接後續頁面（型錄預覽之後由後續階段承接）。
- 不在本期：步驟 6 型錄預覽之後的流程（調整順序、版面配置、型錄完成、發布型錄、型錄連結、型錄列表）；關鍵字篩選（之後再加，時程待確認）。
- 依賴：US-11；US-07（各商品類型的測試資料）。
```

### 工單範例（有畫面）

這張建單時，規劃編號已經變成 10.7，所以標頭寫「開單前重查」。下面各節用送進 Jira 的 `#` 標題寫；放在草稿分頁時改成粗體段落。

```
# T-12｜[示範版型錄系統] 快速型錄品項選擇：自動挑選、換品項與篩選

- 對應故事：US-12
- 專案：ABC
- 類型：Story
- Epic（Parent）：E10 示範版型錄系統（ABC-70）
- 建議規劃編號：10.6（開單前重查）
- Priority：High
- Story Points：5（待重估）
- 指派：不掛（Story 不掛人，負責人掛在子任務）
- Labels：{照專案的標籤規則}

# 1. Story Goal 目標
這是快速型錄流程的步驟 5：品項選擇，本期流程走到這一步為止。現行型錄系統的自動挑選、換品項、篩選都在前端計算，商品資料來自舊版商品庫。原型改用新版商品庫的商品資料；自動挑選與換品項沿用現行在前端計算，篩選條件沿用現行的分類。店家進頁時，系統已依各商品類型的數量挑好品項，店家可以逐項換品項、用分類篩選。

# 2. User Story 使用者故事
* 作為 — 店家
* 希望 — 系統依我設定的數量自動挑好品項，並能逐項換品項、用分類篩選
* 以便 — 不用一項一項挑，也能做出我要的型錄

# 3. Scope 範圍
## 3.1 In Scope
* 系統依範圍與商品類型設定自動挑選品項。
* 上方顯示已選商品類型統計，下方列出已選品項。
* 逐項「換品項」，換成範圍內同商品類型、還沒被選的另一項。
* 自動挑選與換品項沿用現行做法，在前端計算。
* 用「分類」篩選品項，沿用現行規格。
* 頁尾「下一步」：本期停在品項選擇頁，不接後續頁面。
* 型錄系統後端依範圍與商品類型回傳品項清單；商品資料用既有的批次取資料介面取得。

（圖：品項選擇頁截圖）
畫面示意（現行型錄系統）：① 已選商品類型統計 ② 已選品項 ③ 換品項 ④ 分類篩選。灰框不在本期（型錄預覽之後的流程）。

（圖：頁尾截圖）
畫面示意（現行型錄系統）：⑤ 頁尾「下一步」，本期停在品項選擇頁。

## 3.2 Out of Scope
* 步驟 6 型錄預覽之後的流程（調整順序、版面配置、型錄完成、發布型錄、型錄連結、型錄列表）：本期停在品項選擇頁，型錄預覽之後由後續階段承接。
* 關鍵字篩選：之後再加，不在本期，時程待確認。

# 4. Deliverables 交付內容
1. 型錄系統後端 API：依範圍與商品類型回傳品項清單，每項帶商品編號、商品類型、分類、供應商。
2. 型錄系統前端品項選擇頁：自動挑選、已選商品類型統計、已選品項列表、換品項、分類篩選。

# 5. Acceptance Criteria 驗收條件
* AC-01 Given PM 已完成範圍選擇與商品類型選擇，When 進入品項選擇頁，Then 系統已依商品類型設定自動挑好品項，品項都在 T-10 選的範圍內。
* AC-02 Given 前端送出範圍與商品類型，When 型錄系統後端回傳品項清單，Then 回傳的品項都在範圍內，且每項都帶分類。
* AC-03 Given 品項選擇頁已自動挑好品項，When PM 看頁面上方的已選商品類型統計，Then 各商品類型的數量跟商品類型選擇頁設定的一致。
* AC-04 Given 已選品項列表，When PM 瀏覽列表，Then 每一項都顯示新版商品庫的商品資料。
* AC-05 Given 已選品項列表中的任一項，When PM 按「換品項」，Then 換成範圍內同商品類型、還沒被選的另一項，商品類型不變、品項不重複。
* AC-06 Given 品項選擇頁的篩選條件是「分類」（沿用現行），When PM 選一個分類篩選，Then 只顯示該分類的品項。
* AC-07 Given 本期流程走到品項選擇頁為止，When PM 看頁尾「下一步」，Then「下一步」不接後續頁面，畫面停在品項選擇頁（型錄預覽之後由後續階段承接）。

# 6. Definition of Done 完成定義
* AC-01～AC-07 全部通過
* 程式碼通過 Code Review（至少 1 位 Reviewer）
* 相關文件已更新：型錄系統後端品項清單 API 的說明（文件位置待確認）
* 已部署到開發環境，或具備部署條件

# 7. Dependencies 相依項目
* **父**：E10 示範版型錄系統（ABC-70）
* **前置**：T-11（快速型錄商品類型選擇）、T-07（各商品類型的測試資料）
* **後置**：無
* **關聯**：ABC-139（商品資料呈現方式）

# 8. Risks 風險
| Risk | Impact | Mitigation |
| --- | --- | --- |
| 篩選沿用現行的分類，但新版商品庫目前沒有分類欄位（已列入延後處理清單；舊版商品庫只有關鍵字）。現行分類的資料從哪裡來、新版商品庫的商品資料帶不帶得出，待確認。 | High | 篩選本期要做，盡可能符合原本功能；做不出來代表新版商品庫缺資料。開工前請商品資料系統後端確認分類的資料來源；確認前，AC-02、AC-06 無法驗收。 |
| 組合商品、多規格商品、預購商品、訂閱商品四種商品類型的測試資料，要等 T-07 交付。 | Medium | T-07 交付前，先用已匯入的商品類型的資料開發與測試；這四種的資料到了再補測（時程待確認）。 |
```

### 非工程工作的差異

非我方執行、非工程的工作（例：各品類編輯填表），拿上面的格式改三處：

- 類型用 Task；User Story 從我方寫：「作為 — 我方 PM；希望 — 收到各品類編輯填好的類型對照表；以便 — 下一階段大量匯入時，有清單可以跟工程師對接、推動校正與匯入率」。
- 驗收只寫我方驗得了的：「AC-01 Given 各品類編輯填完的類型對照表，When 我方 PM 檢查四個工作表，Then 四個工作表都填寫完成，每一列都註明對應的商品類型。」
- 完成定義用非工程類的三條（見「各節寫法」）。
