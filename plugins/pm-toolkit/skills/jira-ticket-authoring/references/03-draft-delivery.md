# 批次草稿的交付

一次 3 張以上，或使用者要先看草稿時讀這份。草稿確認後，才進待裁示與建單。

## 一、形狀

使用者故事與工單分開放。使用者原話：「我喜歡你給我使用者故事跟工單分開，我可以先快速檢視使用者故事而不用細看工單」。使用者會先掃完故事，再挑工單細看。

### 有線上文件工具（Claude Docs 連接器）時

交付成一份線上文件，不只放本機檔案：使用者要直接在線上改（原話：「你把它出成artifact文件我在線上改比較快」）。分頁如下：

```
{文件名稱，例：下一期使用者故事與工單草稿}
├── 使用者故事               標題＋日期與作者；依系統分組的 US-01～US-NN
├── Jira 工單草稿（母分頁）   格式說明＋工單清單表
│   ├── T-01 {短名}
│   ├── T-02 {短名}
│   └── …                   每張工單一個子分頁
├── 還沒定的事               集中的問題清單（選項、建議、使用者的回答）
└── 改動紀錄                 這一版改了什麼
```

**「Jira 工單草稿」母分頁**依序放：

1. 一句話：一張工單一個分頁，共幾張。
2. 格式說明：描述幾節、AC 用 Given／When／Then、Story 不掛人、子任務由執行者開、標題沿用專案寫法、參考附連結。
3. 點數的讀法：「待估」是還沒估；「N（待重估）」要在 Planning 重估。
4. 截圖的讀法：紅框是本期範圍，灰框不在本期。
5. `## 工單清單` 表格，每列的第一格連到該工單的分頁：

| 分頁 | 標題 | 組別 | 畫面示意 |
|---|---|---|---|
| T-12 快速型錄品項選擇（連到分頁） | [示範版型錄系統] 快速型錄品項選擇：自動挑選、換品項與篩選 | 型錄系統 | 2 張 |

**工單子分頁**：標頭＋9 節（見 02-description-format.md）。分頁名稱「T-NN 短名」。子分頁的排序鍵用補零的編號（`b01`、`b02`…），清單才會照編號排。

**還沒定的事、改動紀錄**各自一個分頁，不進任何工單分頁：工單只寫現在要做什麼。改動紀錄每一筆寫日期、改了哪幾張（用標題）、一句話原因。

連接器的操作照它的指示：動手前讀 guide，建分頁看 `topic.tabs`，放圖看 `topic.uploads`。

### 沒有線上文件工具時

寫本機 markdown：

- 每張工單一個檔，例：`T-01-組合商品匯入.md`。
- 全部故事一個檔：`使用者故事.md`。
- 另外兩個檔：`還沒定的事.md`、`改動紀錄.md`。

寫檔前先問使用者要放哪個資料夾。不寫進 skill 目錄。

目標檔已經存在時，停下來問要覆寫還是另存。使用者可能已經在檔案裡改過；而本機同時留著舊稿與新稿，也曾讓使用者開錯檔。另存時，檔名要看得出哪份是新的。

## 二、截圖

有畫面的工單附現行畫面的截圖，讓讀的人一眼看到本期做到哪裡。

- **紅色實線框＋編號**：本期要做的範圍。編號對應 In Scope 的項目。
- **灰色虛線框**：不在本期。只標工單明寫「不在本期」、而且畫面上看得到的。
- 圖放在 In Scope 清單之後，每張圖下一行圖說：

  > 畫面示意（現行型錄系統）：① 已選商品類型統計 ② 已選品項 ③ 換品項 ④ 分類篩選。灰框不在本期（型錄預覽之後的流程）。

- 工單清單表的「畫面示意」欄寫張數。

### 做法（實測可行）

- 需要瀏覽器工具（Claude in Chrome）。沒有就跳過截圖，告訴使用者哪幾張單少了圖。
- 框直接畫在頁面上再截：用 JavaScript 在頁面注入 `position:fixed; pointer-events:none` 的框（紅框 `2px solid red` 加編號，灰框 `2px dashed gray`）。量元素座標和畫框要在同一次 JS 呼叫裡做，因為視窗尺寸會中途變。
- 要留的截圖存到磁碟（`save_to_disk: true`），不帶 `scale`。帶了 scale，存下來的就是縮小版，離開頁面後補不回來。
- 圖片進線上文件：文字全部填完再上傳圖。上傳照連接器 `topic.uploads` 的說明（實測流程：Artifact 上傳 asset → Docs 建 blob → 在段落後插入圖）。

### 個資與測試資料

- 截到帳號名稱、門市、顧客姓名等個人資訊，截之前用注入的色塊遮掉。
- 為了截圖要在現行系統建立資料（建一份型錄、下一張訂單）時，先得到使用者同意。名稱用一看就是測試的字樣（例：顧客「測試顧客」、門市「測試門市」）。
- 會留下紀錄或影響真實使用者的動作不做：不送出訂單、不指派給真實門市、不發布。實例：在下單頁送出訂單，店家端就會多一筆訂單紀錄。

## 三、多人同時改的守則

使用者會直接在線上改草稿，你和子代理也在改。下面四條都是實際踩過的。

1. **用標題認工單，不用編號。** 使用者會重排編號（例：把 T-18 改成 T-05，再刪掉一張）。派子代理改文件時，給它標題當鍵。實例：照舊編號貼參考清單，12 張貼錯，事後照標題對回才修好。
2. **動手前先讀上次之後的變更。** Claude Docs 用上次讀到的版本號讀差異。寫入被守衛拒絕，代表對方剛改過：以對方的版本為準，不強制覆寫。
3. **「寫入成功」不等於內容對。** 子代理的回報要用獨立來源比對：把文件匯出，逐行對回來源。
4. **先建新的、驗證，再刪舊的。** 換掉一個分頁或一段內容時，新的寫好、驗過，才刪舊的。中途失敗時，至少還有一份完整的。

## 四、每輪回饋之後

- 先判斷回饋是不是前提（會影響多張單）。是就回掃全部故事與工單（SKILL.md 第二段）。
- 把這一輪改了什麼記進「改動紀錄」。
- 回答了的問題，在「還沒定的事」標上答案，不刪題：使用者要能回頭看當初為什麼這樣定。
