# 筆記格式規範

本文件定義學習筆記的格式要求。所有筆記必須遵循以下規範。

## 整體原則

- 語言：繁體中文，技術術語保留英文
- 語氣：專業、嚴謹、客觀，避免俚語或修飾詞
- 格式：標準 Markdown，針對 Notion 最佳化
- 直接以 Markdown 輸出，不要包裹在程式碼區塊中
- 不要加註腳引用（如 ¹ ² ³ 上標數字），也不要在文末附引用來源表格

## 內容結構規則

### 層次結構

- 使用清晰的層次結構，對主題進行邏輯分類和子分類
- 每個主要章節開始時可提供該章節的學習目標或核心問題
- 將長篇論述轉化為簡潔的要點清單

### 標記符號

- `> 📖` — 補充說明、類比、舉例。用於解釋重要但複雜的概念，或以具體案例示範抽象規則
- `> 💡` — 核心結論或關鍵洞察。用於每個主要部分的重點提煉

**📖 與 💡 在注意事項中的行為差異：**
- `> 📖` **可以**出現在注意事項區塊內部，作為獨立的補充說明段落（例如用具體範例解釋某條規則）
- `> 💡` **不可以**以 blockquote 形式出現在注意事項中。若 💡 的內容屬於注意事項，必須轉為列點（`- ` 開頭）

### 表格

- 使用表格比較不同的系統、模型或概念（如同步 vs 異步、不同索引類型）
- 對於同一抽象層次的多個概念，優先使用表格呈現
- 可在比較表格中加入「結構類比」欄，用日常類比輔助理解（如：B-tree → 電話簿排序）
- 比較表格應放在正確的抽象層級。例如「各索引類型的類比」屬於索引類型總覽，不應放在多欄索引章節

### 程式碼區塊

- 務必指定語言（如 `sql`、`shell`、`python`）
- 不要在程式碼前加命令提示字元（如 `=>` 或 `$`）
- 在複雜概念後添加實例或具體場景來說明抽象概念

### Anti-Pattern

- **只在原文有明確的「不要這樣做」語句時才加入**。沒有明確反模式的章節不要硬塞
- 嵌入到對應的章節中，不集中到文末
- 使用 blockquote 格式：`> **不要...** 說明`
- 若有 BAD/GOOD 範例對照，附上程式碼區塊
- **去重規則：** 當 Anti-Pattern 與注意事項或缺點描述同一件事時，刪除注意事項/缺點中的重複描述，保留 Anti-Pattern 版本（因為 Anti-Pattern 有更明確的語氣和範例）

## 章節子區塊結構

### 適合完整結構的章節

描述具體功能、技術或工具的章節，可拆分為：

1. **定義** — 是什麼
2. **使用情境** — 什麼時候用
3. **優點** — 好處
4. **缺點** — 壞處
5. **注意事項** — 列點格式，每一條都是 `- ` 開頭
6. **Anti-Pattern** — 原文明確指出的反模式（沒有就不加）
7. **範例** — 程式碼或實際案例

並非每個章節都需要全部 7 個區塊。根據內容決定哪些適用，不要產生空的區塊。

### 不適合完整結構的章節

入門說明、簡短概念、操作指南等，不要強制套用上述結構。保持自然的段落結構。

**核心原則：不要用內容遷就結構，針對可這樣做的部分再進行調整。**

## 注意事項的格式要求

- 注意事項必須使用列點格式（`- ` 開頭）
- 不要在注意事項中以 `> 💡` blockquote 呈現內容，應轉為列點
- `> 📖` 區塊可在注意事項區塊內部出現，作為某條規則的補充舉例說明（不需要轉為列點）

## 輸入來源處理

### PDF
- 分批讀取，每次最多 20 頁
- 先讀取前幾頁了解結構

### 網頁
- 使用 WebFetch 取得內容
- 注意排除導航、廣告等非內容元素

### 其他格式
- 影片逐字稿、投影片等：按段落或頁面順序處理
